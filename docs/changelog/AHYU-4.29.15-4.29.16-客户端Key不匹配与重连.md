# AHYU 4.29.15 / 4.29.16 — "用不了、一直在重连" 的真因：客户端 Key 不匹配

## 现象

用户报"这个软件在使用中重连"。查用量表：近一小时 **35 条请求全部失败，耗时 1~11ms**，
`model` / `渠道` / `Key标签` 三列全空——这是**在鉴权那一层就被拒**的特征，不是上游问题。

进一步用 `ss -tnp | grep 8321` 看连接的进程名：连上来的是 `io.github.mangi.eta`（代鱼自己），
也就是"客户端"就是代鱼，而应用日志里那句话把原因写得很直白：

```
[WARN] 客户端 Key 与服务端不一致（401）：请把设置页「客户端密钥」重新复制到客户端（客户端 Key=（未设 Key））
```

## 根因（两个问题叠在一起）

1. **客户端的 Key 是空的**。代鱼这边的模型配置里没有填 Key，而网关只要设了 Key 就一律 401。
   以前这句 401 **完全静默**（日志里只有一行"用时 3ms"），所以只表现为客户端不停重连。
2. **网关的 Key 会"每次启动换一个"**。`Config.load` 原来的写法是
   `if (!k.isEmpty()) c.apiKey = k;` —— 文件里的 `apiKey` 一旦变成空串（例如某次配置重写），
   就退回类字段默认值 `sk-cpa-local-<随机>`，而且下次保存会把这个新随机值写回磁盘。
   于是客户端**永远对不上**，重启一次换一把，表现为"怎么弄都不行"。

## 改法

- **4.29.15**
  - `Server.route`：401 时写一条**限流告警**（每 60 秒最多一条），把"客户端 Key 与服务端不一致、
    请重新复制设置页的 Key"写进应用日志（可随"导出"带走）。原来这里是完全静默的。
  - 设置页 Key 旁边加**「复制」**按钮：一键把当前 Key 放进剪贴板。
- **4.29.16**
  - `Config.load` 修正空 Key 语义：**文件里有 `apiKey` 字段就照实采用（哪怕是空串）**，
    只有"老配置根本没有这个字段"才用默认值生成。
    空串的语义明确为"**本机免鉴权**"；局域网模式仍然强制要求 Key（`Server.route` 里那条检查不变）。

## 验证

- `curl` 不带任何 Authorization 打 `/v1/chat/completions`（model=auto, max_tokens=4）：
  **HTTP 200 + 正常 completion**；`/health` 也从 401 变成 200。
- 代鱼那边的 401 风暴停止（最近两分钟无新请求），此前是每 6~8 秒一条。
- 网关进程 13062、`/health` 200、版本 4.29.16。

## 留给以后的注意

- 代鱼的模型配置里现在**不需要**填 Key；如果哪天想恢复鉴权，在设置页填一个 Key 并把它同步到客户端即可
  （两边不一致时会立刻在日志里看到那条 WARN，不会再"静默重连"）。
- 诊断这类"重连"的三板斧：① 用量表看耗时（1~10ms＝本地拒，秒级＝上游）；
  ② `ss -tnp | grep 8321` 看到底是谁在连；③ 导出应用日志看有没有 401 告警。
