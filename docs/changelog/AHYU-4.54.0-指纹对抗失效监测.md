# 4.54.0 — 指纹对抗失效监测（含一次真机误报的教训）

## 起因

4.53.3 让 Claude Code 真的能用了：上游按 system 里有没有官方客户端的自我标识
来做渠道校验，网关只对 WorkBuddy 上游把三枚指纹做零宽混淆（`RiskPrompt`）就绕过了。

但这个做法**建立在一个随时可能不成立的前提上**：上游是**按字节特征**匹配的。
上游只要在判据前先做一次 Unicode 归一化（NFKC 会直接吃掉 U+200C），
混淆就整体失效 —— 而失效的表现**和修复前一模一样**，还是 11128。

4.53.3 的 changelog 把这个的排查入口写成「日志里搜『已混淆 N 处』对不上请求数」。
那是**人肉对账**，实际没人会做：真出事时，用户报"Claude Code 又不行了"，
排查的人看到 11128，会先怀疑账号、额度、UA，而真正的原因没有任何一条日志指出来。

这一版把它变成**机器判定**。

---

## 一、判据：为什么不能只看"混淆过 + 被拦了"

第一版就是那么写的（混淆痕迹在 + `channel_soft` 拦截 ⇒ 报失效），
写完之后在真机上发起一次带完整指纹的 `/v1/messages`，**立刻抓到了它的假警报**：

```
13:44:28  告警：指纹已混淆但仍被内容风控拦下（累计 1 次）
          而这一整条 curl 最终返回的是 HTTP 200
```

原因不在判据的实现，在判据本身：**11128 有两种成因，混淆只能治其中一种**。

| 成因 | 同账号的表现 | 混淆能治吗 |
| --- | --- | --- |
| 内容指纹 | 中性请求**能过**，混淆请求被拦 | 能 |
| 账号被上游标记（真机存在的形态：国内号常年 11128） | 中性请求**也**过不去 | **不能** |

那一次 curl 里，候选列表的第一个账号正是被标记的那种：它对每一份 body 都回 11128，
网关按顺序换到下一个候选、成功交付、整体 200。**内容没有任何问题，
是第一个账号本身在挨罚** —— 第一版把它报成了"对抗失效"。

假警报的代价是真失效时没人信，所以这一版改成**同账号对照**，三条同时满足才确证：

1. **被拦的这份 body 里确实带着我们插进去的零宽字符** ——
   从真正要发出去的那份 body 现查（`carriesNeutralization`），不靠计数推断；
   只看 system 消息（`deFingerprint` 也只动 system），别处的零宽字符不算我们的手笔。
   账号级的那一族 11128（`conversation id missing` / `request illegal`）
   本来就走不到这里 —— `Http.softChannel` 只认 `unapproved channel` /「请重新发送」
   这一族措辞，两种成因的文案判据分得开。
2. **同一个账号最近有过中性请求成功**（24 小时内）——
   说明它没被整体标记，被拦就只能是内容的原因。
3. **那次中性成功晚于最近一次"混淆请求成功"** ——
   若刚才还有混淆请求通过，说明对抗此刻有效，这一单被拦是抖动，不算失效。

代价说清楚：**账号只跑 Claude Code 流量时会漏报**（中性通过无从记录）。
这是刻意的取舍 —— 假警报的代价是真失效时没人信，漏报只是排查慢一点。

## 二、监测放在哪、为什么

| 位置 | 记什么 |
| --- | --- |
| `WorkBuddy.buildBody` | 一次出站尝试，以及这次实际混淆了几处（`noteSent`） |
| `WorkBuddy.chat` 成功交付（首次与重发两处） | 这笔成功了，按 body 里有没有混淆痕迹分记"混淆成功"/"中性成功"（`noteOk`） |
| `WorkBuddy.chat` 的 `channel_soft` 分支 | **重发用尽、确认放行不了**的那一刻记一次拦截（`noteBlocked`） |

最后一条的**位置**是有讲究的：不能记在每次重发上，否则一次请求被记成 3 次拦截，比例全失真。
另外重发用的是 `body2`、判定时传的是 `body` —— 两者都由同一个 `buildBody` 构造，
混淆痕迹必然一致，等价。

`Diagnostics.summary()` 末尾加一行，诊断包里直接可见：

```
指纹对抗：出站尝试 19 · 已混淆 1 · 内容风控拦截 0（失效确证 0）
```

非 0 时行尾带 `⚠ 对抗可能已失效`。日志里的告警首次必报，之后每 20 次确证再报一次
（避免持续刷屏把 `logs.txt` 淹掉）。

## 三、自检：重点不是"能不能报警"，是"该不该报"

新增第 58 项「指纹对抗失效监测（已混淆仍被拦才报警，账号级不误报）」，
把上面两次真机踩到的**假警报形状**固化成用例，以后再改判定逻辑会立刻变红：

| 用例 | 期望 |
| --- | --- |
| 从没成功过的账号 + 混淆请求被拦 | **不**确证（被标记账号的形状，真机实测踩到） |
| 中性请求被拦 | **不**确证 |
| 同账号：中性通过 → 混淆请求被拦 | **确证** +1，摘要出现警示 |
| 同账号：中性通过 → 混淆通过 → 混淆被拦 | **不**确证（抖动，真机实测踩到） |
| user 消息里自带的零宽字符 | 不算证据 |

### 两个自检自身的坑（都改掉了，记一笔）

1. **自检会污染生产状态**。诊断包的生成顺序是**先写 `summary.txt`、后跑自检**，
   所以自检如果"跑完清零"，用户为了取证导出一次诊断包，反而把这次取证要用的证据抹掉了。
   改成**快照/还原**（`snapshotFullForTest` / `restore`），自检只读不写。
   快照必须**深拷贝**账号表 —— `HashMap` 的浅拷贝让两边共用同一个 `long[]`，
   还原时写回去的还是被自检改过的那个数组，等于没还原。
2. **自检会制造假故障**。它会**故意**造一次完整的失效对照来验证判据，
   不加处理的话每跑一次自检（App 启动、设置页、导出诊断包）就往 `logs.txt`
   写一条 ERROR 级的"对抗很可能已失效"—— 看起来像真故障，而这恰恰是这个类要防的事。
   加了 `muteAlerts()`，自检期间只计数不写日志。

断言一律用**相对增量**（从摘要里读计数做差），不用绝对值 ——
进程里随时有真实流量，`出站尝试 2` 这种绝对断言必然假失败。
取不到计数时 `counter()` 返回 `-1`，断言因此失败而不是静默通过。

## 四、验证

- 真机自检 **58 / 58** 通过（含新增的这一项）。
- 真机发起带全部三枚指纹的真实 `/v1/messages`（`system` 里同时有
  `x-anthropic-billing-header`、`You are Claude Code, Anthropic's official CLI…`、
  反馈链接里的 `claude-code`；模型 `hy3`）→ **HTTP 200**，回答正常。
- 随后导出的诊断包：`summary.txt` 为
  `指纹对抗：出站尝试 19 · 已混淆 1 · 内容风控拦截 0（失效确证 0）`；
  `logs.txt` 里**没有任何**失效告警 —— 包括上面那次"第一个候选被标记"的情况，
  在新判据下不再误报（旧版在同一形状下报过）。

## 未做 / 边界

- **账号只跑 Claude Code 时判据凑不齐第 2 条，会漏报**。取舍见上文；
  若将来要想办法覆盖，可以在换号成功时也记一笔"该账号曾放行过混淆请求"，
  但那会削弱第 3 条的抗抖动能力，需要先想清楚再说。
- 计数器是**进程内**的，重启清零。理由：账号状态本来就会变，
  留着上次启动的陈旧"中性成功"记录比清零更危险（可能拿几小时前的证据豁免现在的告警）。
- 只监测、不自动处置。真报失效时不会自动关掉混淆或改策略 ——
  上游改判据的应对方式需要人判断（换别的混淆字符？换表达方式？），
  机器猜一个改法可能把"还能用"变成"不能用"。
