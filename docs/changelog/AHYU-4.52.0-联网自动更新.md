# 4.52.0 — 联网自动更新（多源 + 签名校验 + 一键安装）

## 起因

用户提出：「弄个联网自动更新，最好是无感更新，这样人家也不用下载了。」

先说清一条**做不到的事**，这是整个设计的边界：

安卓从 8.0 起**不允许普通应用静默安装 APK**。要静默必须满足其一：
root、系统签名、或设备管理员。本项目三条都不具备（也不该去要）。
绕过它才是危险的 —— 那道系统确认框本身就是安全机制，
它保证没有任何东西能在用户不知情时装应用。

所以目标定成**把"无感"推到系统允许的极限**：
检查与下载全自动、完全静默；安装只需点一下通知。

## 实测（决定设计的三次测量）

### 1. 镜像不代理 GitHub API

用 curl 逐项实测（2026-10-22）：

| 目标 | 直连 | ghfast.top | ghproxy.net |
| --- | --- | --- | --- |
| `api.github.com` | 200 | **403** | **403** |
| `raw.githubusercontent.com` | 200 | 200 | 200 |
| release 资产（APK） | 302→200 | 200 | 200 |

**推论**：查版本**不能走 GitHub API**。本机网络现状是"国际站经常需要代理"，
用 API 的话没开代理的用户自动更新会**整条静默失效**，而且不报错。
改成读仓库里的 `version.properties`（版本号唯一来源，本来就该读它）—— 三源都通。
Release 说明改成只在用户主动检查时去 API 取一次，取不到就显示"无说明"，不影响更新。

### 2. 三个源下到的 APK 字节完全一致

```
sha256 16af1da1a56d6e00675dde5a258a884ae055e395279f7c9fa213cd46cd398cc9  direct.apk
sha256 16af1da1a56d6e00675dde5a258a884ae055e395279f7c9fa213cd46cd398cc9  fast.apk
sha256 16af1da1a56d6e00675dde5a258a884ae055e395279f7c9fa213cd46cd398cc9  proxy.apk
```

镜像本身不改文件，风险在"源被替换"—— 而这正是签名比对要拦的。

### 3. versionCode 是递增号，不是从版本名推算的

`version.properties` 里 `version.code=657`，而版本名是 `4.51.9`。
若按"主*10000+次*100+修"推算 4.52.0 → 45200，和 657 一比**永远认为有新版本**，
于是每天下一个同样的包、每天弹一次通知，而日志里全是正常字样。

这是本次实现里最容易写错、且**写错了完全不报错**的地方。
所以：版本号与 versionCode **都从 `version.properties` 读**，不做任何推算。

## 改动

- 新增 `core/Updater.java`：查版本（多源）/ 下载（多源）/ 校验 / 安装。
- 新增 `InstallResultReceiver`：收 `PackageInstaller` 结果，装成功后清理下载包。
- `Config`：新增 `autoUpdate`（默认开）与 `lastUpdateCheck`。
- `GatewayService`：
  - 看门狗每轮调 `handleAutoUpdate()`，按天限频；
  - 新增 `ACTION_INSTALL_UPDATE`，由**前台服务**接这个动作发起安装 ——
    不能让通知直接 startActivity：后台启动 Activity 在 Android 10+ 会被拦，
    用户点「立即更新」会**什么都不发生**。这是唯一一个"不报错、只是不响应"的坑。
- `SettingsActivity`：更新按钮改成真更新（原来只跳发布页），新增自动更新开关。
- `AndroidManifest.xml`：`REQUEST_INSTALL_PACKAGES` 权限。
- 自检新增 `checkUpdater`（48 项）。

## 三道安全闸

1. **只升不降**：包里读出的 versionCode 必须**大于**当前（防被诱导装回有漏洞的旧版）。
2. **签名必须一致**：证书 SHA-256 比对，不一致直接删文件拒绝安装。
3. **只从既定源下**：不接受外部传入 URL。

另外**安装前会再校验一次**：下载可能是几天前完成的，期间文件可能被改动。

## 验证

- 真机自检 **48 / 48**（新增「自动更新：只升不降 + version.properties 解析」）。
  该断言钉住两处静默失效：`>=` 写成"永远有新版"、以及 versionCode 推算错误。
- `/v1/debug/update-check` 真机实测：
  - 查版本成功（源：直连），读到 `versionCode=657` 与当前一致 → `newer=false`；
  - 下载成功 1058278 字节；
  - 校验走到"versionCode 没有高于当前"被拒 —— **只有签名先比对通过才会走到这一步**，
    所以这恰好证明了下载 + 签名校验整条链路是通的；
  - 下载包与本机签名指纹一致（`45a99822…`）；
  - 下载残留已清理。
- `canRequestPackageInstalls=false`（实测），确认"安装未知应用"确实需要用户授权，
  界面已按此引导（点「立即更新」弹对话框 → 去设置 → 回来再点）。

## 发版后补做的端到端验证

4.52.0 发布之后，本机（4.51.9）与线上之间终于具备"真的有新版"的条件，
于是把原先标为未验证的那一段补测了：

| 环节 | 结果 |
| --- | --- |
| 更新源可读（三源） | 直连**当时不可用**；ghfast.top / ghproxy.net 均返回 `version.code=658`、`version.name=4.52.0` |
| 三源下载 4.52.0 | 三个源都下到 1066470 字节，sha256 **完全相同**（`cf950581…`） |
| 签名比对 | 下载包证书 `45a99822…` 与已装 4.51.9 **完全一致** → 校验放行 |
| 版本闸 | 包内 versionCode 658 > 已装 657 → 放行 |
| 覆盖安装 | `pm install -r` **Success**，`versionName=4.52.0`，数据保留 |

**直连当时不可用这件事本身就是多源设计的价值证明** —— 如果只走直连，
那次检查会静默失败。镜像兜底让"查版本"这一步在直连挂掉时仍然成立。

仍未验证的一项：**系统确认框的实际点击交互**（`PackageInstaller` 那条路）。
上面用的是 `pm install`，绕过了应用内的 `PackageInstaller` 会话。
要验证它需要界面上点一次通知；本机网关当时处于"用户主动停止"状态，
不适合强行拉起，留待日常使用中确认。

## 一处被实测推翻的假说（保留在此，避免以后重犯）

实现时我在注释里写了"`GET_SIGNATURES` 在 API 28+ 对 v2/v3-only 的包返回空签名"。
**这是未经验证的假说，实测不支持**：

```
sigViaOldApi               45a99822b5bca888...
sigViaNewApi               45a99822b5bca888...
sigViaOldApiOnArchive      45a99822b5bca888...
rawSignaturesLen           1
```

本机（Android 16 / API 36）两条路都能读到，指纹完全相同。注释已改成实测结论：
仍然走新 API 是因为旧 API 已被官方废弃、行为在 v2/v3-only 包上**没有跨版本保证**，
而不是因为"老 API 一定读不到"。

## 未验证 / 已知限制

- **系统确认框的界面交互未实测**（见上节：走的是 `pm install`，
  没走应用内的 `PackageInstaller` 会话）；`InstallResultReceiver` 的
  成功回调与清理也因此未实测。
- 系统确认框无法规避，这不影响使用但确实要用户点一下。
- 镜像可用性会变。三源实测可用（2026-10-22），但都是第三方服务，
  全失败时静默等下次（不影响手动检查）。
