# 4.52.1 — 连接慢与「启动网关」按钮自己变回去

## 起因

用户报了两件事，都在同一个动作上（点「启动网关」之后）：

> 「连接性吧它连接线贯通的不够通，他有时候还会重连。特别慢。」
> 「启用之后它会自动关掉那个按钮。」

两条看起来是两件事，实测下来是**两个独立的缺陷**，各有各的根因。

---

## 一、慢：额度耗尽被误判成限流

### 真机日志（这是全部推理的起点）

```
22:40:38  WorkBuddy 1/deepseek-v4-pro     暂避 300 秒
22:40:38  WorkBuddy 1/deepseek-v4.1-flash 暂避 300 秒
22:40:38  request failed: upstream HTTP 429 {"code":14018,"msg":"额度已用尽…"}
```

一条请求 10.6 秒：先撞一个候选、等它失败、再撞下一个，三个候选全来自
**同一个没额度的账号**。

### 根因：一个字符串匹配漏了中文

`Http.kindOf()` 决定这次失败按哪一类退避，判据只有一个字面量：

```java
static boolean quota(String body) {
    return body != null && body.toLowerCase(Locale.US).contains("insufficient_quota");
}
```

那是 OpenAI 的写法。而 WorkBuddy / CodeBuddy 的额度耗尽长这样：

```json
{"error":{"data":{"code":14018,"msg":"额度已用尽，请访问以下链接，购买加量包以获取更多额度：…"}}}
```

**整条没有一个英文字面量**，于是它落进 `rate`（普通限流）。后果不是文案不好看，
而是三条链路同时走错、而且**一条都不报错**：

| 链路 | 落进 rate 的后果 |
| --- | --- |
| 退避时长 | `rate` 走 429 默认 **5 分钟**，`quota` 是 **30 分钟**。额度不会 5 分钟恢复 → 每 5 分钟白撞一轮，永远撞不出一句成功 |
| 账号级回避 | `accountScoped()` 只认 `quota`/`auth`，`rate` 不进表 → "这个账号没额度了"**从来没被记成账号级事实**，后面每个请求还是要把它名下的模型逐个撞一遍 |
| 界面文案 | 显示"被上游限流（换账号/换模型可继续用）"，而真相是"额度没了，换模型也救不了"—— 用户照着提示换模型，白换 |

真机上 `deepseek-v4-pro` 与 `deepseek-v4.1-flash` **在同一秒**各记了一次
"暂避 300 秒"，正是"退避按限流走"的直接证据。

### 改法

`Http.quota()` 补齐判据（中文 + 几种英文说法）。刻意**不**收单独的 `"quota"` 一词：
OpenAI 兼容中转站的 `"quota exceeded"` 常常指分钟级速率配额，那确实会自己好，
按 30 分钟回避反而是误伤。只认"用尽/耗尽/exhausted"这类**不会自己恢复**的说法。

判据的措辞与展示层 `Detect.CREDITS_OUT` 保持一致（两处要一起改），
自检里有一条专门断言把这两处钉在一起，防止以后漂开。

### 实测验证

改前 —— 额度用尽时仍在逐个撞候选：

```
22:40:38  上游限流：暂避 300 秒 → WorkBuddy 1/deepseek-v4-pro
22:40:38  上游限流：暂避 300 秒 → WorkBuddy 1/deepseek-v4.1-flash
```

改后 —— 一次就记成账号级事实：

```
22:51:58  上游额度耗尽：暂避 30 分钟 → WorkBuddy 1/deepseek-v4-pro
22:51:58  账号级回避（quota）：WorkBuddy 1 名下所有模型暂避 30 分钟 —— 换模型也救不了这个账号
```

请求耗时（同一个 `auto` 请求连发，自动选路）：

| | 样本 | 耗时 |
| --- | --- | --- |
| 改前 | 5 次 | 5006 / 2967 / **11889** / 2620 / 2508 ms |
| 改后 | 4 次 | 574 / **779** / **889** / 8933 ms |

剩下的那个 8.9 秒**不是同一类问题**，日志能看清：

```
23:03:43.001  → hy3              （2.48s）
23:03:45.482  上游回空：暂避 45 秒 → WorkBuddy 1/hy3
23:03:45.483  → step-5-preview   （6.15s）
23:03:51.634  上游回空：暂避 45 秒 → WorkBuddy 1/step-5-preview
23:03:51.637  → minimax-m3.1-flash（0.25s，额度用尽）
```

前两个候选是**上游回了 200 但正文为空**（`empty`），这个回避已经记了 45 秒，
但它们前面还没有被撞过、且在候选里排在前面，所以第一次仍要各等一次。
`empty` 的回避是 4.51.1 就有的机制，两条链路都对；这是单账号场景下无法避免的一次成本
（池子里没有别的账号可换）。**这一点没有变好也没有变坏**，如实记在这里。

## 二、「启动网关」按钮自己变回去

### 根因：还原文案时无条件覆写

`toggleGateway()` 点下去会把按钮改成「正在启动…」，700ms 后还原：

```java
Ui.setLoading(primaryButton, true, "正在启动…");   // tag 存下"启动网关"
...
primaryButton.postDelayed(() -> {
    Ui.setLoading(primaryButton, false, null);      // ← 无条件写回"启动网关"
    refreshStatus();
    ...
}, 700);
```

而 `refreshStatus()` 由**每 2 秒一次的状态轮询**驱动，会写：

```java
primaryButton.setText(running ? "停止网关" : "启动网关");
```

两个写者撞在同一个 700ms 窗口里：

```
toggleGateway():  setLoading(true, "正在启动…")   → tag = "启动网关"
轮询 refreshStatus(): setText("停止网关")          ← 网关起来了，写对了
toggleGateway():  setLoading(false) → 写回"启动网关"  ✗ 把新状态盖掉
```

更糟的是紧接着那句 `refreshStatus()` 会**因为指纹没变而直接 return**
（`running` 早就是 true 了，`lastStatusPrint` 已经记过），所以它**不会纠正**。

用户看到的就是"点了启动，按钮又自己变回启动（像被关掉了）"。
而按钮的语义就是意图判据（`Gateway.state().isAlive()`），再点一次就真的走进
**停止**分支把网关关掉 —— 这就是用户说的"启用之后它会自动关掉那个按钮"。

### 改法

还原前先确认"按钮上现在显示的**仍是**我们写进去的那句进行中文案"：

```java
if (shouldRestoreLoadingText(b.getText(), st.busy)) b.setText(st.restore);
```

期间没别人改过才还原；被别人改成新状态了就保留别人的（那是更新的状态）。
为此把 `setLoading` 记的东西从"只存原文案"改成存**原文案 + 进行中文案**一对。

## 三、顺手修掉一条假红（自检自身的缺陷）

改完之后冷启动自检出现 **51/52**，红的是「缓存价成本分段」：

```
价格表里带缓存单价（cr）的条目只剩 0 条 —— 重建 model_prices.json 时
很可能把 cr 字段丢了，成本会静默退回按全价计算
```

**这是假红。** `Prices.countCachePriced()` 在表还没加载完时返回 `0`，
而自检把 `0` 读成"cr 字段丢了"。价格表是在后台线程加载的，冷启动那一次自检
跑赢了它。同一份包紧接着重启就是 52/52。

假红的代价不是"多看一条红字"——**它训练人忽略自检**，于是一次真的 cr 丢失
会被当成"又是那个竞态"。所以加了 `countCachePricedOrUnknown()`：
没就绪时返回 **-1（未知）**，调用方选择**跳过**而不是报错。
真机连续冷启动 3 次，3 次都是 52/52。

## 改动清单

- `core/Http.java`：`quota()` 补齐中文与多种英文"用尽"说法（并说明为何不收单独 "quota"）
- `core/Router.java`：账号级回避表 `ACCOUNT_AVOID` + `accountScoped/accountAvoided/
  accountAvoidCount`；`score()` 里 `accountAvoided → -80`（**扣分不硬挡**，理由见下）
- `core/Prices.java`：新增 `countCachePricedOrUnknown()`，区分"0 条"与"还没加载"
- `Ui.java`：`LoadingState` + `shouldRestoreLoadingText()`，还原前确认没被别人改过
- `core/Selftest.java`：新增 3 条断言（51→52 项中的 3 条）
- `README.md` / `version.properties`：4.52.2 / 660

## 一处被实测推翻的想法（保留在此，避免以后重犯）

账号级回避**最初写成了硬挡**（在 `candidates()` 里直接跳过被回避账号的所有模型）。
实测把它推翻了：

| 模型（同一账号） | 结果 |
| --- | --- |
| `step-5-preview` / `hy3` | 502（上游空响应，**仍然可达**） |
| `deepseek-v4-pro` / `glm-5.2` | 14018 额度用尽 |

也就是**额度至少部分是按模型计的**。硬挡会把还能用的模型一起误伤，
极端情况下候选池清空变成 404。所以改成 `score()` 里扣 80 分：
它让整个账号排到后面，但池子里没别的可选时仍然能用它。
自检里三条断言钉住这个取舍：只认 quota/auth 是账号级、被回避的账号仍在候选池里、
扣分幅度要"低于正常账号但不盖过 -200 的额度断崖"。

## 验证

- 真机自检 **52 / 52**（连续 3 次冷启动均通过）
- 额度归类：改后日志出现「上游额度耗尽：暂避 30 分钟」+「账号级回避（quota）」
- 请求耗时：改前含 11.9 秒的样本，改后 4 次里有 3 次落在 0.6~0.9 秒
- 按钮：`shouldRestoreLoadingText` 的两种情形（没人改过 / 被别人改成新状态）各有断言

## 未验证

- 按钮那条修的是**判据**（纯函数已钉住），但真机上的"点一次就好"没有在
  修复前后各录一段对照 —— 那个窗口只有 700ms，需要手动复现时序。
- 上游回空（`empty`）导致的首次等待仍在，见上文；它需要**多个账号**才能缓解，
  不是这一版能修的。
