# 4.58.0 — 工具探活对坏模型无限重试：114 次、106 次 HTTP 500

## 起因

`ToolAbility` 的后台探活（"这个模型到底会不会真的调工具"）逻辑是：
`state() == UNKNOWN` 就探一次，30 秒内不重复。**失败时它什么都不记**——
不写模型画像（对：一次 500 说明不了工具能力），**但也没记失败本身**。
于是 `state` 永远停在 UNKNOWN，下一个带工具的请求又探一次。

真机日志：

```
17:54:19 [WARN] 工具探活失败（WorkBuddy 1/glm-5.1）：HTTP 500
17:54:51 [WARN] 工具探活失败（WorkBuddy 1/glm-5.1）：HTTP 500
   …
07:29:13 [WARN] 工具探活失败（WorkBuddy 1/glm-5.1）：HTTP 500
```

同一个模型 **114 次**，其中 **106 次 HTTP 500**，跨了 13 个小时。

代价两层：

1. 每次探活都是一次**真实上游调用**，114 次全部落空；
2. 这段时间两个账号本来就在撞额度耗尽（14018），探活还在持续消耗额度，
   等于自己给自己加压。

## 改法

三条，都是纯加法：

**1. 失败退避。** 记住每个 `账号/模型` 的连续失败次数，翻倍退避
（1 → 2 → 4 → 8 → 16 → 32 分钟，封顶 30 分钟）。探活**成功**（无论最后结论是
native / bad / 没下结论）立即清零——那时模型可用，没理由继续躲着它。

**2. 账号在回避里就不探。** `Router.accountAvoided()` 已经知道这个账号正在
额度/凭证回避中，此时探活只会再撞一次同样的墙，而这次调用还算在用户账号上。

**3. 失败仍然不写模型画像。** 这一条是原有的正确行为，本次特意保留并在注释里写死：
HTTP 500 / 超时 / 额度耗尽都不是"这个模型不会用工具"的证据。
写进去会让 Router 把一个好模型从候选池里踢掉。

## 验证

自检新增第 62 项「工具探活失败退避（坏模型不再每 30 秒重探）」，断言：

- 初始状态没有退避；
- 第一次失败后就有退避；
- 第二次失败后**等得更久**（翻倍），且不超过封顶。

自检 **62/62 通过**（真机，4.58.0）。

## 未做 / 边界（重要）

- **没有在真机上观察退避的实际效果**。账号当前全部撞在额度/频率上，
  探活必然失败，但也正因为如此，"退避把 30 秒变成 1 分钟、2 分钟……"
  这件事要等一个正常工作的账号才能看到日志上的差别。
  本版证据是**日志统计（114 次 / 106 次 500）+ 自检断言**。
- 退避参数（基数 1 分钟、封顶 30 分钟、翻倍）是拍定的，没有按真实分布调参。
- 退避状态只活在进程内，重启清零。这是刻意的：重启后重新试一次是对的，
  代价只是一次失败。
- 没有改"探活该不该在额度耗尽时也算一次调用"这个更上层的问题。
