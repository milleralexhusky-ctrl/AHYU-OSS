# 4.51.2 — 首字延迟、候选重试与重连

## 起因

客户端反馈“连接时间太长，完全反应不过来”“重试次数太多”，日志里出现过：

```
Anthropic 流式第 1 个候选失败（Loomy 2）：Socket closed
POST /v1/messages 用时 102180ms
```

一条连上了但迟迟不吐字的上游，会一直占着请求：

- 首 token 看门狗默认 **90 秒**（竞速才 30 秒）；
- 流式响应头要等内容提交才发，客户端在等待期间看不到任何字节，
  自己的超时先到，于是表现为“一直重连”；
- 空响应/断连的候选没有短期回避，下一条请求还会先试它。

## 改动

### 首字更快、更早看到字节

- **响应头与 `: ready` 立即下发**：`DeferredWriter.open()` 只开头、不提交内容；
  内容继续缓冲，仍可换候选。实测首字节 **3.7ms**，总耗时 1.35s（此前同类请求 102s）。
- **首 token 预算按位置分档**（`serveWithBudget`）：
  - 轮换中还有下一个候选：**10 秒**；
  - 最后一个候选 / 点名模型：**45 秒**；
  - 竞速保持 30 秒；单条直连仍可用默认 90 秒。
  首 token 到了看门狗就撤销，不影响后续长输出。

### 少重试

- 轮换候选上限从 4 收紧到 **3**；失败不会再无限拉长一轮。
- `EmptyUpstream`（200 但无正文/思考/工具调用）立即给该“账号/模型”
  **45 秒短回避**：下一条请求先去试别的候选，不在回空的模型上重复等。
- 工具能力探活增加**每账号 30 秒一次**的节流：以前一轮轮换会对同一账号的
  多个候选各起一次 `get_weather` 探活，既费额度也容易被上游当成异常活动。
- `DeferredWriter` 在换候选时 `reset()` 缓冲；一条请求只写一次响应头，
  不会出现两个 `message_start`/两份 SSE 响应。

### 失败收尾

- 响应头已经发出（`: ready`）但所有候选都失败时：
  - Anthropic：写 `event: error`；
  - OpenAI：写 `data: {"error":…}` 后补 `data: [DONE]`；
  不再尝试往已提交的流里写第二个 HTTP 响应。

## 验证

- 真机自检 36 / 36。
- Anthropic `auto` 流式：`starttransfer=0.0037s`，`message_start → content_block_*`
  序列正常，总耗时 1.35s。
- 已知回空模型：非流式返回 502；流式在 head 已发出时走 SSE error 事件。
- 受限 WorkBuddy 账号仍在本地直接拒绝，不产生上游请求。

## 未做

- 没有做“并行对冲（hedging）”：它能在首字慢时再开一路，但会成倍增加上游请求，
  与“少重试/省额度”的目标冲突；先把串行预算压到 10 秒，观察真实收益再决定。
- 上游账号本身的速度无法改变；本轮优化的是网关等待、换候选和收尾的方式。
