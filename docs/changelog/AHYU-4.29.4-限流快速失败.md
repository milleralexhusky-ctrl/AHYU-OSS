# AHYU 4.29.4 — 上游确认限流时快速失败

## 一、起因：真机上一次持续的重试风暴

客户端（跑在手机上的编码 agent）反复报 `Runtime 运行失败` / `重连失败`。网关日志里同一时刻
是这样的（每 ~10 秒一轮，连着一堆）：

```
W CPA: 上游限流：暂避 1717 秒（不计失败、不进熔断）→ WorkBuddy 1/kimi-k3-1
I CPA: 流尚未输出，换下一个候选重试：WB1/kimi-k3-1
W CPA: 上游限流：暂避 14677 秒（不计失败、不进熔断）→ WorkBuddy 2/kimi-k3-1
W CPA: upstream error（2 个候选都失败）: upstream HTTP 429 {"code":6004,
       "msg":"您的使用量已超出频率限制，将在 2026-10-16 05:00:11 UTC+8 重置，
       您也可以切换其他模型继续使用。", ...}
```

两个事实叠加：

1. `kimi-k3-1` 只有 WorkBuddy 1 / 2 两个账号提供，而**两个账号都被上游限流**；
2. 上游在正文里**写明了恢复时刻**（05:00:11），可网关每次请求仍然把两个账号各撞一遍。

于是每一轮都是：1.6 秒 + 两次注定 429 的往返，然后失败。上游一次也没成功过。

## 二、根因：`throttleUntil` 里混着两种性质不同的值

`Router` 的限流回避只有一个 `throttleUntil` 字段，但它装着两类东西：

| 来源 | 例子 | 性质 |
| --- | --- | --- |
| 上游正文/`Retry-After` 明写 | "将在 2026-10-16 05:00:11 UTC+8 重置" | **事实** |
| 我们拍脑袋的默认退避 | "429 了先躲 5 分钟" | **猜测** |

`pickAll()` / `pinnedThenFallbacks()` 的策略是"不可用的**沉底但不丢弃**（全冷却时仍要能发）"
—— 这是刻意设计：按猜测值拒绝，可能把一个其实已经恢复的账号挡在门外。但它没法区分
"我们猜的 5 分钟"和"上游说的 5 个小时"，所以连**上游明说的事实**也照样去撞。

## 三、改法

把两种值拆开存：

- `Router.Stat` 新增 `throttleResetAt` —— **只**在 `fromUpstreamClock = true` 时写入
  （即上游正文里解析出了恢复时刻）；
- 新增 `Router.confirmedThrottleUntil(key)`，只认这个字段；
- `Server` 新增 `confirmedBlockUntil(cands, model, tries)`：**本次会尝试的候选全部**都被
  确认限流时，返回最近的恢复时刻；只要有**一个**候选没被确认限流就返回 0（放行）；
- 四个直连路径（OpenAI 兼容 / Anthropic / Gemini / Responses）在候选循环**之前**插入检查。
  位置很关键：在 `startSse()` **之前** —— 流式请求一旦写出响应头就只能把错误塞进流里
  （客户端表现为"流断了"），而在这里拦下还能正常返回 **HTTP 429 + JSON**。

```java
long blockedUntil = confirmedBlockUntil(cands, req.model, tries);
if (blockedUntil > 0L) {
    writeAllThrottled(out, r.path, req.model, blockedUntil, tries);
    return;
}
```

**刻意的边界**：只看上游明说的时刻，不看我们估的退避。所以"全冷却时仍要能发"对
猜测值完全保持原样，行为零变化；只有"上游已经告诉我们几点恢复"这种情形才提前拒绝。

## 四、验证

### 端到端（真机，同一把客户端 Key）

```
第 1 条（让它去学限流）: [HTTP 200] 用时 1.0557s   ← 撞了上游两个账号
第 2 条: {"error":{...预计 10-16 05:00 恢复，本次未向上游发起请求...}}
        [HTTP 429] 用时 0.0107s                    ← 11 毫秒
第 3 条: 同上 [HTTP 429] 用时 0.0113s
```

日志侧确认第 2、3 条**没有**产生任何新的"暂避"记录（即没有上游往返）：

```
W CPA: 请求 WB1/kimi-k3-1：全部 2 个候选都被上游确认限流到 10-16 05:00，
       本次不向上游发起请求（省掉 2 次注定 429 的往返）
```

1.6 秒 + 2 次上游往返 → **11 毫秒 + 0 次**，而且客户端拿到的是标准 429 + 一句能看懂的话。

### 离线跑真实代码

`Server.confirmedBlockUntil()` 需要一个 `Server` 实例，离线可以直接构造
（`Server(Config)` 只存一个字段），于是把**真实方法**拉起来断言：

```
ok   认上游明说的恢复时刻
ok   估的退避不算确认限流
ok   有候选可用时不拦
ok   全部被确认时拦下
ok   返回最近的恢复时刻
ok   已过恢复时刻不再拦
ok   tries=1 时只看第一个
THROTTLE_TEST_PASS
```

### 内置自检

新增第 15 项「限流快速失败只认上游明说的时刻」，真机 15/15 通过。它钉住三条语义：
上游明说 → 记住；上游没说（我们估的）→ 不算确认；时刻已过 → 不再拦。

## 五、顺带确认的事（给用户的结论）

限流是**按模型**的，不是按账号。同一个 WorkBuddy 1 账号：

- `WB1/kimi-k3-1` → 429（限流到 05:00）
- `WB1/hy3`、`WB1/glm-5.3`、`WB1/deepseek-v4.1-flash` → 正常

所以客户端把模型从 `WB1/kimi-k3-1` 换成 `auto` / `auto-code` 立刻恢复可用
（实测两者都 200、约 2 秒）。这也是上游那句"您也可以切换其他模型继续使用"的字面意思。
