# 4.53.3 — 让 Claude Code 真的能用

## 起因

用户报：「但是其他的。客户端又是可以用的。你需要做的就是让他支持。Claude Code。」

这句话推翻了上一版（4.53.2）的结论。我当时认定「账号没有额度，这不是网关能修的」——
因为余额接口说周期剩余是 0、推理接口一律回 14018。**用户是对的，我错了**：
同一个账号、同一时刻，别的客户端能用，说明额度不是问题，
问题在网关发给上游的请求形状上。

这一版找到并修掉了**三个叠在一起的原因**，最后真机跑通。

---

## 一、Claude Code 的模型名被本地白名单挡住（它连请求都不发）

### 现象

给它 `ANTHROPIC_MODEL=auto`，它立刻退出，网关日志**干干净净一条请求都没有**：

```
[claude-code:unrecognized_model] {"model":"auto","query_source":"sdk"}
```

换成官方名字 `claude-sonnet-4-5-20250929` 就变成：

```
There's an issue with the selected model (claude-sonnet-4-5-20250929).
It may not exist or you may not have access to it.
```

—— 这次它**发了**请求，但网关回 404「没有账号提供模型 claude-sonnet-4-5-20250929」
（本机目录里是 hy3 / glm-5.3 / deepseek-* 这些）。

**两头都过不去**：网关认得的名字，客户端本地就拒；客户端肯发的名字，网关不认得。

### 改法

`Server.compatModel()`：客户端发来的 Anthropic 官方模型名，**只在本地目录确实没有它时**，
映射到虚拟模型 `auto`。

为什么映射到 `auto` 而不是某个具体模型：映射到具体模型等于替用户挑模型，那个模型一坏整条路就断；
`auto` 才是本机的正确语义（按成功率/延迟/成本自己选，能换号能换模型）。

边界写死在代码里并进了自检：
- 只在本地真的没有这个名字时才映射 —— 用户自己挂了同名 Claude 中转的话，点名就照点名走，绝不抢；
- 只认 `claude-*` / `anthropic.claude-*` / `claude.` 形状，不误伤 `glm-5.3`；
- 带账号前缀的点名（`WorkBuddy 1/claude-...`）不改写，那是用户明确的路由意图。

## 二、上游按**提示词内容**做渠道校验（三个指纹）

这是最关键、也最费劲的一条。

### 现象

`400 11128 Illegal API invocation from an unapproved channel`，
官方提示「请求被拦截，请重新发送」。README 里一直把它记成"请求级风控、重发就能过"，
但**换号、换 UA、换 realm、重发都没有用**，100% 复现。

### 排查：先排除"是不是账号问题"

用同一账号、同一模型、只改提示词内容做对照实验（各 8 次）：

| system 内容 | 结果 |
| --- | --- |
| `You are a helpful assistant.` | **0/8** 被拦 |
| `You are Claude Code, Anthropic's official CLI for Claude.` | **8/8** 被拦 |

轮流交替跑，结果完全稳定 —— 是**内容**，不是账号、不是随机风控。
再用 OpenAI 入口发同样的 system，同样被拦；换中性内容就通过 ——
与协议入口无关，就是那串字。

### 三个指纹（各自独立触发，都实测必拦）

| # | 指纹 | 出处 |
| --- | --- | --- |
| 1 | `x-anthropic-billing-header` | Claude Code 2.1.308 把它自己的计费头**当成第一个 system 块**塞进请求体 |
| 2 | `You are Claude Code, Anthropic's official CLI for Claude.` | 官方客户端的自我描述句 |
| 3 | `claude-code` | **最隐蔽**：藏在系统提示末尾的反馈链接 `github.com/anthropics/claude-code/issues` 里 |

第 3 个是靠**二分定位**抓出来的：修完前两个后，整份真实请求体（45 KB）仍然 100% 被拦。
把 27 KB 的 system 块切前缀二分，收敛到第 5800~5804 字节，落在那个 URL 的 `code` 上。
单独发那个 URL 不触发（它是长上下文里的一枚"证据"，不是独立关键词），
用整份真实请求体换成 ZWJ 写法后 **8/8 通过**。

### 改法：`RiskPrompt`，零宽混淆

不删、不改写，只在词内插一个零宽非连接符（U+200C）：

```
You are Claude Code, ...        →  You are Claude‌ ‌Code, ...
https://github.com/anthropics/claude-code/issues
                                →  https://github.com/anthropics/claude‌-‌code/issues
x-anthropic-billing-header      →  x-anthropic-billing-‌header
```

**为什么不是删掉整句**：那是把"你是 Claude Code"这条真实且有用的信息从提示词里拿掉，
改变模型看到的内容 —— 降质，不是修复。零宽字符人看不见、模型读到的语义完全一样，
上游那套字节级特征匹配则不命中。

**只在 WorkBuddy 上游生效**：别的渠道没有这个风控，改它们的提示词是没必要的风险。

## 三、`auto` 在候选被限流时会整池变空 → 503

### 现象

修完前两条之后变成 `503 虚拟模型 auto 暂时没有可用候选`，
而同一个模型点名调用（`hy3`）**正常返回**。

### 根因

两条路径对"被限流/冷却"的候选处理不一致：

| 路径 | 被限流的候选 | 后果 |
| --- | --- | --- |
| 点名模型（`pickAll`） | **沉底**，不丢弃 | 还能用 |
| 虚拟模型 `auto`（`Router.candidates`） | **直接剔除** | 全被挡时整池为空 → 503 |

而账号级额度回避（`credits==0 → -200`）会把所有候选一起压低，
两者叠加就出现"每个模型单点都能用、`auto` 却说没有候选"。

### 改法

`Pick` 加 `sink` 标记：冷却 / 限流 / 半开试探中的候选**沉底而不是剔除**，
分数压到 `-1e6`（低于任何正常候选，账号级回避最低也就 -280 左右）。
正常时它排最后（等于回避），别的候选都失败时仍有机会被试到。

注释里写清了为什么：上游的"此刻被挡"不等于"这一轮注定失败"
（实测同一个 WorkBuddy 账号下 hy3 通了、wb-lite 报 14018），
硬剔除只会把"暂时不可用"升级成"没有可用候选"，
而 agent 客户端遇到 503 会一直重试 —— 用户看到的就是"卡住不出字"。

## 改动清单

- `core/RiskPrompt.java`（新）：三枚指纹的零宽混淆，保持大小写/空格/分隔符原样
- `core/WorkBuddy.java`：`deFingerprint()` 在 `buildBody` 里对全部 system 消息生效
- `core/Server.java`：`compatModel()`；7 个协议入口的 parse 之后统一调用
- `core/Router.java`：`Pick.sink`；限流/冷却候选沉底而非剔除
- `core/Selftest.java`：新增 2 条（55 → 57 项），覆盖指纹混淆与模型名兼容

## 验证

- 真机自检 **57 / 57**
- 对照实验：同一账号同一模型，中性 system **0/8** 被拦、含指纹 **8/8** 被拦
- 整份真实 Claude Code 请求体（45 KB、12 个工具、27 KB system）：
  修复前 **100% 11128**，修复后 **8/8 通过**（非流式 5 次 + 流式 3 次）
- `auto` 不再 503（改为如实报上游的 14018）
- 发布包 `/v1/debug/*` 仍全关

## 自检抓到了我自己的两个 bug（保留在此）

1. **断言写错了**：我断言混淆后应含字面量 `ClaudeCode`，但实现是"空格两侧各插一个零宽字符"，
   这个字面量本来就不该出现 —— 假失败。改成断言"指纹串不再原样存在 + 去掉零宽后逐字等于原文"。
2. **预筛大小写敏感**：`neutralize` 开头的廉价预筛用小写 `indexOf`，而正则是 `(?i)`，
   于是 `CLAUDE CODE` 全大写形态被预筛放过去、指纹漏网。自检的全大写用例抓到了它。

两个都是"看起来在跑其实没生效"的那类问题，值得单独记一笔。

## 未做 / 已知限制

- 指纹混淆是**内容指纹对抗**，上游改判据就可能失效（比如改成先归一化零宽字符）。
  真失效时的表现是 11128 复现。~~排查入口：日志里搜「已混淆 N 处」对不上请求数。~~
  **4.54.0 起这件事已机器化**，不用再人肉对账：`FingerprintWatch` 做同账号对照
  （同一账号中性请求能过、已混淆请求被内容风控拦下），成立才在日志里报
  「零宽混淆对抗很可能已失效」，诊断包 `summary.txt` 也有
  `指纹对抗：… （失效确证 N）` 一行。判据与取舍见 4.54.0 的 changelog。
  当时写"人肉对账"是因为还没有这个计数器 —— 那是**没人会做**的排查方式，
  这条正是被 4.54.0 取代的。
- 用户的 WorkBuddy 账号**确实额度紧张**：可用模型在 hy3 / kimi / minimax 一带，
  `deepseek-v4-pro` / `glm-5.2` / `wb-lite` / `auto` 直接报 14018。
  这一版让"能用"的模型真的能用，不改变"哪个模型有额度"。
- `auto` 依次撞到没额度的模型时会较慢（每个失败要等一次 429 往返）。
  这是上游额度现状，不是网关能修的；点名有额度的模型（如 `hy3`）最快。
