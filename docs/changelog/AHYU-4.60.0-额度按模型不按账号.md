# 4.60.0 — 额度按模型算，不按账号算

## 起因

用户报告：**"我们两个账号好像被封了"**——简单聊天偶尔能过，复杂任务一律被拒；
用全新注册的账号测试，也是同样的拒绝。

排查下来，"封号"是假象，真正的原因是我们自己的判定逻辑把一件**按模型**的事
当成了**按账号**的事，然后连坐。

## 一、先看事实：账号没封，是模型分层的

同一个 WorkBuddy 账号（WorkBuddy 1），同一时间：

| 模型 | 结果 |
| --- | --- |
| `glm-5.3` | 429 + `14018 额度已用尽` |
| `deepseek-v4.1-flash` | 429 + `14018` |
| `kimi-k3-1` | 429 + `14018` |
| **`hy3`** | **200，正常出字** |

而且 `hy3` 不只是"简单聊天能过"——按 Claude Code 的真实尺寸造的请求也过了：

```
131KB · 45 个工具定义 · 30 轮对话 · 22k prompt token → 200，"收到"
```

所以"复杂任务被拒"不成立：`hy3` 不拒复杂请求。用户看到的是**选到了付费模型**，
而那批模型的额度是 0（WorkBuddy 把付费模型的额度单独记账，
免费模型 `hy3` 不受影响）。

## 二、真正的问题：一次 14018 把整个账号连坐 30 分钟

`Router.accountScoped()` 里写着：

```java
return "quota".equals(kind) || "auth".equals(kind);
```

注释的依据是"额度是记在账号上的，跟模型名无关"。这个前提**对 WorkBuddy 已经不成立**。

后果是连锁的：

1. 任意一个付费模型返回 14018 → `recordAccountAvoid(账号, now + 30min)`；
2. 整个账号被扣 80 分（`Router.score`）；
3. `Repeats.wouldSucceed()` 直接 `continue` 跳过这个账号；
4. 于是 `auto` 选路绕开它——**连带把同账号下明明能用的 `hy3` 一起废掉**。

用户看到的现象就完全对上了：账号"好像被封了"、简单请求偶尔能过（撞到 `hy3`）、
复杂任务（`auto` 落到了付费模型）一律失败。

## 三、改动

`accountScoped()` 只保留 `auth`：

- **凭证失效**确实是整个账号的事——换模型也过不了鉴权，按账号挡掉是对的。
- **额度**改由 `账号/模型` 那条 throttle 单独记。换模型就该能过，这正是本次的目的。

顺带把 `Router` / `Http` / `Selftest` 里三处"额度是账号级"的注释改掉，
写明 2026-10-26 的真机证据，免得下次又照旧注释改回去。

## 四、验证

真机（4.60.0 debug）：

```
① 先打付费模型  WB/deepseek-v4.1-flash  → 500（上游 14018）
② 紧接着  auto                          → 200，"收到"
③ 日志：不再出现「账号级回避（quota）」
```

修复前同样的顺序会让账号进入 30 分钟回避，第 ② 步会失败或落到别的账号。
现在第 ② 步直接由 `WorkBuddy 1/hy3` 接住。

## 边界

- 如果某个账号**真的**所有模型都没额度，现在会多撞几个模型才放弃（以前一次就整体回避）。
  代价被 `tries` 上限（最多 4 个候选）兜住，换来的是"免费模型不被误伤"。
- `credits == 0` 仍然会扣分（-200），因为那个字段来自上游的**账号级**余额接口。
  它对 WorkBuddy 也不准（明明 `hy3` 能用却报 0），但这条这次没动——
  要改成"以实际成功为准"需要先有足够样本，留到以后。
- WorkBuddy 付费模型的额度是否恢复、平台策略是否会再变，不是网关能控制的。
  本次只修"不连坐"，不改变"付费模型没额度"这个上游事实。
