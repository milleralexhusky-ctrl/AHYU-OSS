# 4.53.2 — 判重死循环、余额口径、两条协议说法不一致

## 起因

用户报：「还是不行，说什么连接中就是不出来。」

查下去是**三个叠在一起的缺陷**，前两个是我的 bug，第三个是账号状态。

---

## 一、判重把暂时性错误永久化成了硬错误

### 现象

日志里同一条内容从第 3 次一路被拒到第 25 次：

```
检测到重复请求（第 25 次，内容完全相同），已停止转发 → auto
POST /v1/chat/completions 用时 5ms
```

### 根因

`Repeats` 的判据只有「内容指纹 + 次数」。它要治的是"客户端卡在重试循环里、
白烧额度"，但**客户端重试时内容当然是一样的**，于是：

```
账号失败 → 请求失败 → 客户端重试（内容一样）
→ 被判成"卡死重试" → 返回 429
→ 客户端更该重试 → 计数继续涨 → 永远 429
```

**把暂时性错误永久化成了硬错误** —— 账号恢复后也没机会再成功。

### 改法

拦截的前置条件必须是"**这次本来能成功**"。新增 `Repeats.wouldSucceed(cands)`：
候选池里确实有可用账号（额度充足、不在冷却/回避里）时才拦；
池子不可用时只计数、不拦，如实把上游原因报回去。

实测：同一段内容连发 6 次，修复前第 3 次起全 429，修复后 `200 200 200 200 200 200`。

## 二、余额读错字段：显示「还有 500」但一个请求都发不出去

### 现象（同一个资源包、同一时刻）

```
余额接口说：WorkBuddy 1 = 500、WorkBuddy 2 = 500
推理接口说：每个模型都 14018「额度已用尽」
```

### 根因

原始回包里两个字段并存：

| 字段 | 值 | 含义 |
| --- | --- | --- |
| `CapacityRemain` | **500** | 总容量 ← 原来读的是这个 |
| `CycleCapacityRemain` | **0** | 按周期剩余 ← 真正决定能不能用 |

读错的后果是**双向的、而且互相矛盾**：

- 界面显示「积分 500」，用户以为网关坏了，而不是"该换号"；
- 同时 `p.credits=500` 又让它在选路里不被扣分（`credits==0` 才扣 200 分），
  于是每次都去撞一个注定 14018 的账号。

### 改法

`cycleRemain()` 统一取周期字段，`credits()` / `balance()` / `packs()` 三处共用。
关键细节：**"为 0" 和 "字段缺失" 必须分开** —— 0 是"这个周期用完了"的事实，
缺失才是"这个产品线没这字段"、才允许回落到总量。混在一起会让一个用完的包
被总量字段救回来，等于没修。

`balance()` 不再优先信上游的 `TotalDosage`（它就是那个 500 总容量口径），
改为按周期剩余求和；上游原值仍保留在 `upstreamTotal` 里供排查对照。

实测：`可用=0（上游总量字段=500）`——数字不再骗人。

### 顺带纠正我上一版说错的一件事

4.53.0 我说"自动签到领到了 500 → 600（+100），真领到了"。**那个数字不可信** ——
它来自同一个读 `CapacityRemain` 的接口。签到本身确实跑了（上游回 code=10001
「今天已签到」），但"余额涨了 100"这个证据是错的，我不该拿它当"领到了额度"的硬证据。

## 三、同一个上游故障，两条协议说法相反

### 实测

| 路径 | HTTP | 客户端看到 |
| --- | --- | --- |
| OpenAI 非流式 | **200** | `⚠️ 上游账号暂时都不通…`（占位文案，像正常回答） |
| Anthropic 非流式 | **500** | `upstream HTTP 429 … 14018 额度已用尽`（真话） |

OpenAI 那条让用户以为"模型答了这么一句"，看不出真原因是额度耗尽还是渠道校验，
也就不知道该换号。

### 改法

**非流式本来就能改状态码**，没有理由不说真话：改成 502 + 真实原因。
流式做不到（响应头与 `: ready` 在试第一个候选前就发出去了，状态码改不了），
所以兜底文案保留 —— 那是传输层的硬约束，不是取舍。

实测两条路径现在都报 `14018 额度已用尽`。

## 一处我查错又改回来的（保留在此，避免以后重犯）

"连接中就是不出来"我第一判断是**流没闭合**，因为客户端拿到 200 会一直等。
于是写了个 `DeferredWriter.finishFailed()` 去显式关 chunked 流。

写完去核对既有代码，发现 `Conn.endStream()` **早就在做同一件事**（每轮请求结束
都会写 `0\r\n\r\n`）。那半段是**死代码**，删掉了 ——
不留"看起来在修 bug 其实没修"的东西，那比不修更糟（下次有人会以为这里有保护）。

真实的客户端现象见第二、三条：根因是上游 11128/14018 与余额口径误导。

## 改动清单

- `core/Repeats.java`：新增 `wouldSucceed()`，拦截前置条件收紧
- `core/Server.java`：判重移到候选池判断之后；非流式全失败改为如实报错
- `core/WbTasks.java`：`cycleRemain()` 统一周期字段；`credits()`/`balance()`/`packs()` 共用
- `AccountsActivity.java`：正被上游判额度耗尽时，不再单独显示那个数字
- `core/Selftest.java`：新增 2 条（53 → 55 项）

## 验证

- 真机自检 **55 / 55**
- 判重：连发 6 次相同内容，全部 200（修复前第 3 次起全 429）
- 余额：`可用=0（上游总量字段=500）`
- 两条路径：OpenAI 502 / Anthropic 500，都报 `14018 额度已用尽`
- 新断言覆盖：`cycleRemain` 四种形态（周期为 0 / 仅总量 / 两者都无 / 精确值优先）
- 发布包 `/v1/debug/*` 仍全关

## 未验证 / 已知限制

- **用户的账号确实没有额度**，这不是网关能修的。两个 WorkBuddy 账号按周期算
  剩余都是 0，上游一律回 14018。要恢复使用需要换账号、充值，
  或等体验包周期结束（`2026-10-31 23:59:59`）。这一版只是让"为什么用不了"
  变得看得懂，不是让它能用。
- 流式路径仍返回 200 + 兜底文案（传输层约束），只有非流式改成如实报错。
