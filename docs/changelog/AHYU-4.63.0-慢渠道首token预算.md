# 4.63.0 — 慢渠道：首 token 预算可按账号放宽

## 起因

用户接上了云知声（`maas-api`），但 `u2-flash` 一直失败：

```
u2-flash → 500, 用时 45.019s
W CPA: 直连第 1 个候选失败（maas-api）：Socket closed
```

**45.019 秒**这个数字很关键——正好是网关给"最后一个候选"的首 token 预算。
也就是说：上游没有拒绝，是**我们自己等不及，把连接掐了**。

线上表现是 `Socket closed`，看起来像上游挂了，实际是本地超时。这类误判最费时间：
排查的人会去怀疑 Key、额度、模型名，而真正的原因是"这个模型本来就慢"。

对照实验也支持：同一个 `u2-flash`，偶尔能在 35 秒左右返回 200（但正文为空，
因为思考把小预算吃光了）；加上 `chat_template_kwargs: {"enable_thinking": false}`
之后能正常出正文 —— 说明链路是通的，只是慢。

## 改动

账号新增一个开关 **「慢渠道（首 token 等到 120 秒）」**（`Config.Provider.slow`，默认关）：

- 打开后，这个账号的首 token 预算从 45 秒放宽到 120 秒；
- 只影响**这一个账号**，其它渠道的失败判定速度不变；
- 默认关闭是有意的：放宽超时意味着"上游真挂住"时要多等 75 秒才换候选。
  只给明确知道自己慢的渠道开。

同时也把「轮换中还有下一个候选时只等 10 秒」这条规则保留给非慢渠道 ——
慢渠道开不开都不会拖慢别人的换号。

## 用法

账号编辑页 →「限额与能力」下面 → 打开「慢渠道」→ 保存。

云知声 `u2-flash`、Hetzner 的 Qwen3.8（实测 4~7 tok/s）都属于这类。

## 验证

- 真机自检 63 / 63；
- 默认关闭时行为与 4.62.0 完全一致（`slow=false` 走原来的 10s/45s 分档）；
- 打开后的 120 秒预算**没有做真机长跑验证**——需要用户先在账号里勾选，
  再发一次请求才能看到效果。这一点如实记录。

## 未做

- **没有做"自动识别慢渠道"**。理论上可以在首 token 超时两次后自动打开，
  但这会改变用户的显式配置，而且"慢"和"挂"在第一次超时时分不开。
  留给人来判断更稳妥。
- 云知声其它模型（`glm-5.3-flash`、`deepseek-v4-pro` 等）在这把 Key 上是 404
  （`model_not_found`）—— 平台的 `/v1/models` 列的是全量目录，不等于这个 Key 有权限。
  这是上游行为，网关侧无法修正；预设里列出全部模型会误导，留待以后按渠道加白名单。
