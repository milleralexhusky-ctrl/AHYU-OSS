# 4.51.7 — 缓存命中全链路、截断进选路、额度未知不再沉底

## 起因

上一版（4.51.6）做完界面之后做了一次审计，看"网关还有哪里能提升"。三条候选里
两条是**数据链路断在半路**，一条是**排序判据写错**：

1. **缓存 token 被读到之后整个丢掉了。** `Proto.Usage.cached` 一直在解析
   （OpenAI 的 `prompt_tokens_details.cached_tokens`、Anthropic 的
   `cache_read_input_tokens`），但走到 `Conn` 就断了 —— `Conn` 上没有这个字段，
   `usage.tsv` 的 22 列里没有它，`Prices.costUsd` 也只有两个参数、不分缓存价。
2. **截断率算完就扔。** `Stats.Seed.truncRate` 从 4.32.0 起就在算，但
   `score()` 里一个都没用、界面也不显示。
3. **额度未知被当成额度用尽。** `Router.java` 的 `credits <= 0` 把默认值 -1
   读成了"耗尽"。

## 一、缓存命中：从上游到界面的完整链路

| 环节 | 改动 |
| --- | --- |
| `Proto.Usage.cached` | 已有，未动 |
| `Server.Conn` | 新增 `tokCached` 字段 + `copyObs` 转发 + 每请求清零 |
| `Server` 的 tap | `finish()` 里 `c.tokCached = usage.cached` |
| `Usage.Obs` | 新增 `cached`，落成 **`usage.tsv` 第 23 列** |
| `Prices` | 价格表新增 `cr` 字段（缓存读单价）；`costUsd` 加三分段重载 |
| `Usage.Stat` | 新增 `tokCached` / `tokInWithCacheInfo` / `cacheHitRate()` |
| 界面 | 用量页每行显示「缓存 N%」，摘要行也带 |

**为什么这条值得做。** 命中缓存的输入 token 便宜得多 —— 实测源数据里
**中位折扣是输入价的 1/10**（Anthropic 约 1/10、OpenAI 约 1/2）。混在 `tokIn`
里按全价算，会让「成本 ≈$」明显偏高。更要紧的是：**这是会话亲和（4.51.5）唯一的效果指标** ——
亲和存在的全部意义就是让同一段对话复用同一个上游、保住 prompt cache，
而"命中率涨没涨"只有这个数能回答。做亲和时没接上这一环，等于做了个没法验证的功能。

### 新增列只能追加在末尾

`usage.tsv` 现在 23 列。所有读取端一律按 `c.length` 判断列数、缺列当 0/空处理，
所以**旧行不会因为"没有这一列"被读成失败或零值**。中间插一列会打乱 13~22 列的
全部索引，而旧行还躺在磁盘上。

### 价格表补 `cr`

`res/raw/model_prices.json` 是**离线裁剪**生成的，脚本不在仓库里（见 4.27.0）。
这次用 LiteLLM 源里的 `cache_read_input_token_cost` 补了 **1214 条**，
只按归一化名**精确匹配**（不做前缀/家族外推）；缓存价高于输入价的 3 条不采信、丢弃。
文件 272KB → 288KB。

因为重建这张表很容易再次把 `cr` 丢掉（后果是**静默的**：成本悄悄退回按全价算），
自检里放了一条**绊线**：带缓存价的条目数掉到 500 以下就报错。

## 二、截断率进选路

`stopReason=length` 的回答**不是失败**：HTTP 200、有正文、传输层全绿，
熔断看不见、限流退避看不见、`ok` 计数还是成功。于是"这个模型话说到一半就停"
在选路里完全隐形，每次都会选中它，用户拿到半句话却不知道为什么。

现在按截断率小惩罚：

```
v -= 15 * seed.truncRate * trust      // trust = wContent/(wContent+HIST_K)
```

- **上限 -15**，刻意排在"刚报过错"(-50) 之下 —— 截断难堪，但毕竟给了大半句可用的话。
- **按可信度打折**：1 笔样本的截断不该定生死（和延迟项同一个公式）。
- **判据干净**：`Proto.canonicalStop` 在有工具调用时优先返回 `tool_calls`，
  所以 `truncRate` 只统计"纯正文被 max_tokens 切断"，不会把爱调工具的模型冤枉成老是截断。

### 刻意**没**进选路的那个信号

同一个 `Stats.Seed` 里还有个 `contentRate`，这次**没有**用上，原因值得记下来：
它的分母里 `outChars` **只数正文 delta**（见 `Server` 的 tap），
于是"只回工具调用、不吐正文"的响应会被算成"没内容"。拿它进选路会**系统性压低
爱调工具的模型** —— 正好和"agent 场景要能调工具"相反。

自检里为此钉了一条口径断言，顺带说明这个取舍。

## 三、额度未知 ≠ 额度用尽

```java
// 之前
if (c.provider.credits <= 0) v -= 200;   /* 额度用尽 */
// 现在
if (c.provider.credits == 0) v -= 200;   /* 额度确认用尽 */
```

`credits` 默认 **-1**，而全项目只有 `workbuddy` / `trae` / `loomy` 三种类型会刷新它。
原来的判据让 `openai` / `anthropic` / `gemini` / `kimi` / `deepseek` / `doubao` /
`xai` / `cline` / `codex` / `claude` / `antigravity` 这些类型的**每个候选永远背着 -200 分**。
候选总分区间约 100~155，这个惩罚直接把它们沉到池底 —— 表现就是"加了个自定义中转，
`auto` 老是轮不到它"，而且不报错、不写失败，查都没得查。

界面一直是这么理解的（`AccountsActivity` / `AccountDetailActivity` 都是
`if (credits >= 0)` 才显示），**只有路由把 -1 读成了耗尽**。同一份数据两种读法，错的是路由这边。

本机当时只配了 Loomy（会刷积分），所以没被咬到 —— 属于"只要加一个自定义中转就会踩"的潜伏缺陷。

## 四、我自己踩进去又爬出来的那个坑

第一版把命中率写成 `tokCached / tokIn`，真机立刻显示 **「缓存 0%」**——
看上去像"亲和没生效"，实际是**分母算错了**。

原因：升级之后 `usage.tsv` 里会长期混着两种行。4.51.7 之前写的行没有第 23 列
（读出来 cached=0），之后写的才有。用全部历史 `tokIn` 当分母，等于把那批
"根本没有这个信息"的行当成"输入了但一次都没命中"。本机当天 **175M 历史 token**
只对应几百个新 token，比值直接被压成 0。

`Stats` 处理内容信号时**已经写明过同一条纪律**（"旧行不能算进分母，否则会低估"），
我在 `Usage` 这边没照做 —— **同一个项目里同样的坑还是会再踩一次**。
所以加了 `tokInWithCacheInfo` 单独攒分母，并补了一条自检专门钉这个口径。

修好之后：**缓存 91%**。

## 验证

- 真机自检 **45 / 45**（41 → 45，新增四条：缓存价成本分段、额度未知、截断口径、命中率分母）。
- **绊线实测有效**：临时把价格表里 1214 条 `cr` 全删掉并装机 → 自检变红，
  报"带缓存单价的条目只剩 0 条，重建时很可能把 cr 字段丢了"；恢复后 45/45 全绿。
- **缓存链路端到端**：同会话发两跳请求，`usage.tsv` 落盘、
  用量摘要显示「缓存 91%」（分母修好前是 0%）。
- 成本分段：全命中按缓存价、未命中按输入价、命中数超过输入数时夹住（不出现负成本）。
- 发布包 6 次真实请求全部有正文，`/v1/debug/*` = 404。

## 未验证 / 已知限制

- **截断惩罚没有 A/B 对照**。权重 -15 是按"排在刚报过错之下、比延迟项略重"选的，
  不是实测调出来的。它只会影响"多个候选分数接近时选谁"，不会让一个健康的候选
  被排除；但目前**没有数据证明它改善了用户观感**，只是修掉了一个"信号完全不可见"的缺口。
- **`cr` 覆盖率约 45%**（1214 / 2933）。源数据本身就没给部分模型缓存价，
  那部分仍按输入价算（保守，宁可高估）。
- 缓存**写入**（cache creation）的单价没有引入 —— 源数据里只有 339 条有，
  且各家计费口径差异大，这次只做"读命中"这一侧。
- `contentRate` 的口径缺陷（只数正文、不算工具调用）**已记录但未修**：
  它没进选路，暂时只在观测层，改它要同时动 `Server` 的 tap 语义，风险与收益不匹配。
