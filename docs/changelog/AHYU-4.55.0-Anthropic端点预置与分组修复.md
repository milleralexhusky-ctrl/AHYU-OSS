# 4.55.0 — Anthropic 兼容端点预置 + 服务商分组修复

## 起因

用户整理了两份「AI 接口网关」资料（1024 活动平台清单 + 官方订阅转 API 通道），
问这些内容对 AHYU 有没有融入的价值。逐项对照后结论：

- **OpenAI 兼容预设**：AHYU 已有 32 家，比资料列的还全 —— 不必做；
- **New API / One API / LiteLLM**：那是另一套网关软件，AHYU 本身就是网关 —— 不必做；
- **逆向号池（xx2api）**：明确不做，两份资料自己也这么建议；
- **Anthropic 兼容端点预设**：**真缺口** —— 值得做。

缺口的形状：AHYU 的「Claude（API Key）」只硬编码了 Anthropic 官方一个地址。
而国产厂商近几年陆续给编程订阅配了 **Anthropic 兼容端点**（专门喂 Claude Code，
订阅费直接当 API 额度用）：智谱、阿里百炼、DeepSeek、Kimi 都有。
想用它们的用户得自己去翻各家文档、自己判断地址该不该带 `/v1` ——
4.53.1 那个「Claude Code 地址带不带 /v1」的坑就是这么踩出来的。

选完进原有的 ProviderEditor 填 Key，行为与以前完全一致。
**出站逻辑零改动**：这些地址的拼接 `Upstreams.anthropicUrl` 本来就能正确处理
（带 `/v1`、带 `/api/anthropic` 后缀、直接给完整端点都认，见 4.51.1）。

**端点全部实测过**（2026-10-23，空 POST 探测）：
`open.bigmodel.cn/api/anthropic`、`coding.dashscope.aliyuncs.com/apps/anthropic`、
`api.deepseek.com/anthropic`、`api.moonshot.cn/anthropic` 全部 401

拼接规则由 Upstreams 负责，重复补会拼出 `/v1/v1/messages`。

### 2. 修掉「选择服务商」分组的既有缺陷（真机可见）

**现象**：OpenAI 兼容的服务商选择列表里，"智谱 GLM""火山方舟""小米 MiMo"
"讯飞星火""百度千帆""阶跃星辰"全被归到**「国外」**分组下；
「国内」表头出现在第 2 项之后，「国外」表头紧跟在第 4 项，
其后 20 多项不管归属全部挤在「国外」下面。

**两层原因**：

1. **判据漏项**：`isDomestic` 的关键词表只认英文域名片段
   （`siliconflow`/`moonshot`/`bigmodel`…），而预置清单里"智谱 GLM""讯飞星火"
   "小米 MiMo""百度千帆"这些**只写了中文名**，英文关键词表自然漏；
   连 `deepseek` 也不在表里（它靠 TYPE 直判的那条只覆盖同名**渠道类型**，
   OpenAI 兼容形态的"DeepSeek"预设走的是名字匹配，照样漏）。
2. **表头只插一次**：`domesticHeaderDone` / `overseasHeaderDone` 各只允许插一次
   表头，而列表顺序是国内国外**混排**的 —— 即使判据全对，第二个国内条目
   出现在「国外」表头之后也不会再有「国内」表头。两个错误叠加，
   用户看到的是一锅粥。

**修法**：

- 判据下沉到 core 包的 `Region`（UI 包的自检够不着 UI 包的代码，
  放在 UI 包里出过错都没法锁 —— 这次就是靠自检先红了一次"我自己写的断言写反了"，
  才确认它真的在干活）；
- 关键词表补全（英文 + **中文**都收），并加「国际版」例外：
  "MiniMax 国际版"走境外出口，属国外，这条必须在关键词匹配**之前**短路，
  否则名字里的 `minimax` 会把它拉回国内；
- 预置清单**重排为先全部国内（14 家）、再全部国外（19 家）**，
  表头逻辑不动就正确了，方法注释里写明这个约束。

菜单文案顺手改准：「等 16 家预置」→「33 家预置」（清单早就 33 项了）。

### 3. 自检第 59 项

「预置服务商分组（国内/国外判据与预置清单逐个对得上）」：

- 渠道类型直判的 6 种（WorkBuddy/Trae/Loomy 国内，Claude/Codex/Antigravity 国外）；
- 21 家厂商名字逐个断言归属（包括这次全错的 5 家）；
- 「国际版」例外单独一条。

**自检首跑就抓到一个真 bug（我自己写的）**：三条"应判国外"的断言写成了
`!isDomestic(...) return 报错`，逻辑上等于"只要不是国内就报错"——对国外项恒真、
对国内项也恒真，三条同时红。改成 `if (isDomestic(...)) return 报错` 后全绿。
这正是"断言要写正向条件"的教训：`!want` 形式的否定断言在两态判断里极容易写反，
而且写反了**编译器和运行都看不出来**，只有对着期望值逐条核才会炸。
