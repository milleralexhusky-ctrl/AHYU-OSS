# 4.51.8 — 幽灵账号：删掉的账号为什么还会蹦出来

## 起因

用户反馈：「老是蹦出一些不存在的账号，我好像已经把他删了才对，结果他的信息还是出现在那里。」

查下来有**两个互相独立**的来源，都会让人看到"已经不存在的账号"。两个都修了。

## 一、账号快照会复活删除（真正的"蹦出来"）

`Config` 里有一对设计，各自都合理，凑在一起就成了复活循环：

**① 快照只增不减**（`snapshotAccounts`）：

```java
if (now < prev) return;   // 账号变少了 → 不刷新快照
```

本意是防"一次意外写坏的配置把救命快照也冲掉"。代价是：**你删掉的账号永远留在快照里**，
快照冻在"历史上账号最多的那一刻"。

**② 配置一空就从快照整个恢复**（`Config.load`）：

```java
if (loaded.providers.isEmpty()) {
    loaded = recoverFromSnapshot(ctx, loaded);   // 恢复完还会写回 gateway.json
}
```

**③ 删除账号会走到"配置为空"这一步**（`ProviderEditor`）：删到最后一个时
`providers` 变空，`save(a, true)` 允许写空 → 紧接着 `reload()` → 读到的配置是空的
→ 触发 ②，把冻住的旧快照整批捞回来（含你早先删掉的），并写回磁盘。

于是：**删 → 空 → 复活全部旧账号 → 再删 → 又空 → 又复活**。

### 修法：快照要区分"意外写坏"和"用户主动删"

带用户意图的保存（只有删账号、导入/恢复备份会传 `allowEmptyProviders=true`）
必须让快照跟着缩小：

| 情形 | 旧行为 | 新行为 |
| --- | --- | --- |
| 用户主动删到 0 个 | 跳过（快照留着全部） | **删除快照**（不留复活源） |
| 用户主动删到剩 N 个 | 跳过（快照仍含已删的） | 写（快照跟着缩到 N） |
| 自动保存时看着变少 | 跳过 | 跳过（保护，不变） |
| 配置意外读空 | 跳过 | 跳过（保护，不变） |
| 账号变多 / 持平 | 写 | 写 |

判定抽成纯函数 `Config.snapshotAction(now, prev, userIntent)`，
由自检直接喂数字断言 —— 这个 bug **不报错**，只在"配置恰好读空"时发作，
靠手工点几下试不出来。

## 二、行为画像里列出已删除的渠道（"信息还出现在那里"）

这是**第二个、独立的**来源，也是本机实际在发生的那个。

`usage.tsv` 留 30 天，"行为画像"按**历史行里的渠道名**聚合
（`QualityStats.aggregate`），**从不与当前配置比对**。账号删掉之后，
它的名字还会在画像里出现好几天。本机实测：配置里只有 `Loomy 2` / `Loomy 3`，
但画像里列着 `WorkBuddy 1`、`Trae 1`、`Loomy 1`、`debug-*` 一大堆 ——
用户看到的就是"我明明删了，怎么还在"。

### 修法：标记，而不是删除

那些样本是**真实发生过的调用记录** —— "这个渠道以前靠不靠得住"对
"要不要重新加回来"仍有参考价值。用户困惑的是"我以为删干净了"，
不是"这里有历史数据"。所以给它们加一句「（已删除）」，并在报告末尾说明：

```
渠道          样本  p95    可用率  ...
WorkBuddy 1（已删除）1120  13.4s  88%   ...
Loomy 2       454   47.6s  94%   ...     ← 当前账号，不标
```

配置读不到时**一个都不标** —— 把全部渠道打成"已删除"是比不标更糟的谎。

## 三、顺带查清：输出协议没问题

排查过程中顺带核对了宿主（cccoder）与我方网关之间的协议，因为它的日志里
`out=0`、`上下文=?` 看着可疑。结论：**AHYU 的 Anthropic 流式输出是正确的**。

实测 `/v1/messages` 流式响应，事件序列与字段完全符合规范：

```
event: message_start        message{id, type, role, model, content:[], usage{...}}
event: content_block_start  index 0, {type:"text"}
event: content_block_delta  {type:"text_delta", text:"你好"}
event: content_block_stop
event: message_delta        delta{stop_reason:"end_turn"}, usage{input_tokens:11, output_tokens:3}
event: message_stop
```

`out=0` / `上下文=?` 是**宿主自己的统计没解析**，不是网关少发了字段
（`usage` 在 `message_delta` 里给全了，`/v1/models` 也带了
`context_length` / `max_output_tokens`）。

有一处**已知的、刻意的偏差**要说明：`message_start` 里的
`usage.input_tokens` 是 0，真值在 `message_delta` 才给。官方客户端在
`message_start` 就读 input_tokens 做上下文计数，所以它们会看到 0。
这是为"空流不提交、可以换候选"付的代价（`message_start` 延迟到第一段内容才写）。
**未修**，因为要修得先知道 input_tokens，而那只有上游 `message_start` 才有 ——
要保留换号能力就得缓存这个值到第一段内容到达，属于结构性改动。

## 验证

- 真机自检 **47 / 47**（45 → 47，新增"快照不复活"与"历史渠道标记"两条）。
- **决策表实测**：离线跑修复前/后两种规则，确认旧规则在"用户删到剩 2 / 删到 0"
  时都返回"跳过"（快照冻在峰值），新规则分别返回"写"/"删快照"；
  自动保存与意外读空仍然被保护。
- **画像标记实测**：本机配置只有 `Loomy 2` / `Loomy 3`，
  报告里 `WorkBuddy 1` / `Trae 1` / `Loomy 1` / `debug-*` 全部标上「已删除」，
  而 `Loomy 2` / `Loomy 3` 不标。
- 协议核对：实测 `/v1/messages` 流式事件序列与字段。

## 未验证 / 已知限制

- **快照修复只对新发生的删除生效**：本机上已经存在的陈旧快照（含已删账号）
  不会被自动清理 —— 它要等到"下一次用户主动删除"才会跟着缩小。
  如果现在正被幽灵账号困扰，最干净的做法是删掉一次账号（触发重写），
  或者手工删除 `gateway.accounts.json`。
- `message_start` 的 `input_tokens=0` 未修（见上）。
- 画像里"已删除"的判定按**名字**比对：账号改名后旧名字会被标成"已删除"
  （这是对的），但如果删掉一个账号又新建**同名**的，旧的会被误认为仍在
  （同名同类型的账号本来就会被当成同一个，见删除逻辑里的 `sameName` 判据）。
