# 4.61.0 — 文档版本校验 + 出站节流

两件互不相干的事，都是用户提出来的。

## 一、README 的版本号会悄悄过期

用户发现：代码已经是 4.60.0 / `versionCode 674`，README 顶部还写着 **4.53.3 / 664**。
照着 README 核对版本的人会对不上号，而且这种错**不会报错、不会被谁发现** ——
它只是慢慢地和事实分离。

根因是发版流程里漏了一步：`version.properties` 改了、changelog 写了、README 的
自检项数也顺手改了，唯独**顶部那行版本号**没人管。

### 改法：构建期硬校验

`build.sh` 现在会读 README 顶部的

```
- 当前版本：**4.61.0**（versionCode 675）
```

和 `version.properties` 逐字比对，不一致就**直接编译失败**：

```
README 的版本行与 version.properties 对不上：
  version.properties: 4.60.0 (674)
  README.md:          4.53.3 (664)
把 README 顶部「当前版本：**4.60.0**（versionCode 674）」改一致后重跑。
```

为什么是硬失败而不是警告：漏更新的代价是"文档骗人"，而警告在构建输出里
和一堆正常日志混在一起，没人会看见。README 不存在时跳过（不干扰自定义构建）。

## 二、出站节流：别让同一个账号被"机器式连发"

用户提出：**上游识别到异常调用、账号被限、功能突然断掉，都是可能发生的**。

先说实话：今天这一轮的证据更像**产品策略**而不是行为识别 ——
同一个账号下付费模型一律 `14018`、免费模型 `hy3` 却连 131KB 复杂请求都能过，
新旧账号结果一致。按行为判的话不该这么整齐。

但"降低被识别的面"这件事本身值得做，因为网关确实有让同一账号短时间连续收请求的路径：

| 路径 | 原来的间隔 |
| --- | --- |
| 一个请求失败 → 立刻换下一个候选 | 0 |
| `auto*` 轮换一轮最多试 3~4 个候选 | 0 |
| 两个会话同时说话，落到同一账号 | 0 |

真人用官方客户端不会在一秒内发三次。新增 `Pacer`：

- **按账号**（`Provider.name`）限速，同一账号两次出站至少隔 **350ms**，外加 0~250ms 抖动
  （固定间隔本身也是特征，加随机才不像定时器）；
- **不同账号互不影响** —— 竞速三路来自不同账号，不会被串行化；
- 只在"上游刚刚才收过这个账号的请求"时才等。正常一轮对话里用户打字的时间远大于这个间隔，
  体感无变化；真正会等的是重试和并发，而那正是要压的；
- 只加等待，**不改变任何重试/选路语义**；节流出任何异常都吞掉，绝不能把请求带下水。

位置放在 `serve()` 里**真正出站调用之前**：前面的本地限额、并发槽检查都是本地的，
没发出去就不该占用账号的发送配额。

### 验证

```
单发一次                 3812ms
同时发两个（同账号）      并发#2 3500ms / 并发#1 4095ms   ← 第二个多等约 595ms
```

自检新增第 63 项「出站节流」：第一次不等、第二次必须等够间隔、不同账号互不牵连
（后者是竞速的命门，若按全局算会把三路并行排成串行）。断言只用下界，不用上界 ——
慢设备上多等一点是正常的。

## 未做 / 边界

- **这次不改重试次数和竞速路数**。它们是可靠性手段，一旦减少，正常的偶发失败
  就更容易变成用户可见的报错。节流已经把"连发"摊开了，先看效果再说。
- **节流救不了 `14018`**：付费模型没额度是上游计费闸，不是行为识别。
  这条改动只是降低"像机器人"的面，不承诺能解除任何限制。
- README 的版本校验依赖那行文字的格式。如果以后改写措辞（比如去掉 `versionCode`），
  正则就匹配不到、`R_NAME` 为空，会直接报不一致 —— 这是刻意的：宁可构建失败，
  也不要静默跳过校验。
