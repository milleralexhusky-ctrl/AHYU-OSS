# 4.52.1 — 删掉的账号不再从旧快照复活

## 起因

用户报：「我删除账号之后他还会存在，我删了两次，他还会存在。」

上一个版本（4.51.8）已经修过"幽灵账号"，所以第一件事是确认**这次是不是同一个问题**。
`/v1/debug/ghosts` 给出了确凿数据：

```
memoryCount:   3
diskCount:     3
snapshotCount: 6      ← 多出一倍
```

## 根因：4.51.8 只管得住"以后"，管不住"已经冻住的"

4.51.8 修的是"**以后的**删除会同步缩快照"。但用户是在 4.51.8 **之前**删的那批账号 ——
它们的记录已经冻在 `gateway.accounts.json`（快照）里，改代码不会回头动它。

这批旧数据平时不出来（`Config.load` 优先读 `gateway.json`），只在一种情况下整批复活：
**`gateway.json` 因为任何原因读空**（写盘被中断、文件损坏、升级迁移），
`recoverFromSnapshot()` 就把那份 6 个账号的快照当成权威恢复回来。
用户看到的就是"删了两次还在"。

也就是说：**正常的读路径永远看不到这个 bug**，只在"配置恰好读空"时才现形 ——
所以它既难复现，也难归因。

## 改法：load 时按磁盘校准快照

```java
static boolean shouldReconcile(int diskN, int snapN) {
    return diskN > 0 && snapN > diskN;
}
```

`Config.load()` 里，磁盘非空时发现"快照比磁盘多"就按磁盘重写快照。

安全性论证（为什么这不是"用旧盖新"）：**不存在"快照比磁盘新"的正常路径**。
每次 `save()` 都是先写 `gateway.json`、再更新快照，所以磁盘永远不旧于快照；
快照比磁盘多，只能是"删掉的账号还留在快照里"。

**磁盘为 0 时不校准**：那是 `recoverFromSnapshot` 该兜底的场合，
按这条规则校准会把最后的救命快照冲掉 —— 那比幽灵账号严重得多。
自检里专门钉了这一条（`shouldReconcile(0, 6)` 必须为 false）。

## 验证

- 真机装上新包后 `/v1/debug/ghosts`：`snapshotCount` **6 → 3**，
  `memoryCount` / `diskCount` 均为 3
- 自检新增「旧快照按磁盘校准」：先钉决策表（含磁盘为 0 的反例），
  再**直接读真机的两个文件比对**，而不是喂假数据 ——
  以后若再出现"快照比磁盘多"，自检会红，而不是等用户下次丢配置才发现

## 顺带修一处自欺

`/v1/debug/ghosts` 的 `usageChannels` 原先读 `usage.tsv` 的 `c[1]`，
那列是**接口**（吐出来的全是 `/v1/chat/completions` 这类路径），
渠道名在 `c[3]`。一个调试端点报出看着像数据、其实答非所问的东西，
比报错更费时间。
