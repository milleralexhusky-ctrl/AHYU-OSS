# 4.51.5 — 会话亲和：同一段对话优先复用上次成功的候选

## 起因

选路一直是**每请求独立打分**：同一段对话的第 1 轮和第 5 轮可能落在不同账号的
不同模型上。后果有三，都是用户能感知、但很难查的：

1. **prompt cache 全废**。agent 类客户端（Claude Code、各类 CLI/IDE 插件）
   每一轮都把整段历史重发一遍。换模型等于换缓存前缀 —— 每一轮都按全新 prompt
   重新计算并计费。用户看到的是"越聊越慢、越聊越贵"。
2. **风格/格式漂移**。不同模型的工具调用习惯、输出格式都不一样。同一段任务里
   中途换模型，看起来就是"这个网关不稳定"。
3. **工具循环断档**。中途换模型时，上一轮 `tool_call` 的形状未必对得上，
   复杂 agent 任务容易在这里断掉。

## 一、`Conversation.session()`：跨轮次稳定的会话键

不能直接拿 `Conversation.id()` 当亲和键 —— 它哈希的是 **system + 全部消息**，
每多一轮就变一个值（这是它的本职：把"一跳一跳"串起来，见 4.36.0 的
`usage.tsv` 会话 ID）。拿它做"下一轮还走上一个候选"会**永远命不中**。

`session()` 只哈希 **system + 第一条 user 消息**，并优先采用客户端自己声明的
会话提示（`prompt_cache_key` / `user` / `metadata.user_id`）。对话开头在后续
轮次里不变，所以同一段会话的每一轮都得到同一个键。

这个边界与上游一致：WorkBuddy 的 `officialConversationId` 也是按
"system + 首条 user" 派生的（4.36.7），所以不会出现"网关认为是一段、
上游认为是两段"的缓存错配。

只有 system、没有 user 时返回空串，调用方据此跳过亲和。

## 二、`Router` 侧的亲和表

- `SESSION_PICK` / `SESSION_AT`：会话 → 上次成功交付的候选 + 时刻。
- **只在成功交付时写入**（`recordOk` 旁边一起调 `noteSession`），失败的候选
  不进表 —— 下一轮不会再被亲和回那个已经证明不行的候选。
- 容量上限 256 条、TTL 30 分钟，按时刻淘汰最老的一批，内存不会无界增长。
- **按会话存，不按虚拟模型存**：同一段对话里客户端从 `auto` 换到 `auto-code`
  仍然是同一段对话、仍然该复用（真机验证里这条确实生效）。这一点和普通
  路由状态不同，所以亲和表刻意不挂在虚拟模型上。

## 三、与既有机制的三处冲突，逐个处理

实现时发现的三个真问题，每一个都会让亲和静默失效或变味：

**(1) 亲和不能绕过熔断。** `sessionPin` 返回的是历史成功键，它可能已经被
熔断/限流/账号被删挡在候选池外。所以插回队首之前**先在候选表里核对**：
不在池子里就当没有亲和，走原来的逻辑。硬插回去等于给熔断开后门 ——
那正是 4.37.0 修掉的问题。

**(2) 不能排除"pin 就是上一次选中的那个"。** 第一版写了
`pinned != null && !pinned.equals(last)`，看着像是"要换一个才有意义"，
实际上把亲和废掉了：同分轮转（`ROTATE`）已经按轮转计数把并列候选转过一轮，
pin 正好被转下去是完全正常的，那时不把它提回来，亲和就等于没做。
**真机实测第一版就是这么失效的**（日志里候选排序每轮都在转，亲和一次没命中）。

**(3) 客户端重发时必须让反粘连赢。** 同一段对话的后续轮次应该复用，
但客户端**重发同一条请求**时用户要的是"换个答案"，不是复用。用
`Repeats.note(req) > 1` 区分这两种情况：重发时不做亲和，让"连续 N 次同候选
就把队首挪走"的反粘连生效（重发到第 3 次会被直接拦掉，见 `Repeats`）。
`note()` 按 `Req` 对象幂等，`candidates()` 里提前调一次不会让后面的计数翻倍。

## 四、所有协议路径都学到亲和

非 OpenAI 协议（Anthropic / Gemini / Responses / Ollama / Completions）的成败
都汇总在 `Server.recordDirectOutcome` 一处，所以把 `noteSession` 放进它里面，
并给每个调用点补上 `req` 参数。**这一处不能漏**：Claude Code 走的正是
`/v1/messages`，恰恰是最依赖 prompt cache 复用的那个客户端。

竞速路径（`auto-race`）也记：下次同一段对话直接点名那条胜出的候选，
连竞速都不用开。

## 验证

**真机自检 39 / 39 通过**（新增一条「会话亲和」，五项断言）：

- 同一段对话的第 1 轮与第 2 轮派生出**同一个**键；
- `Conversation.id()` 仍然随轮次变化（没把两者搞混，多跳追溯不受影响）；
- 两段不同的对话派生出**不同**的键；
- 客户端声明了不同的 `prompt_cache_key` 时必须分开；
- 只有 system 时返回空串；
- 亲和表：写得进、读得回，空候选名不写坏表。

**真机端到端**（`logcat` 抓选路行）：

```
A1  会话甲 第 1 轮  auto      → Loomy 2/qwen-3.8-max(130) → …
A3  会话甲 第 2 轮  auto      → Loomy 2/qwen-3.8-max(130) → …   ← 复用
C1  会话甲 换 auto-code        → 会话亲和：本轮优先复用 Loomy 2/qwen-3.8-max  ← 跨虚拟模型也复用
B1  另一段对话      auto      → Loomy 3/Kimi-k2.6(126) → …      ← 正常轮转
```

同一段对话里**重发完全相同的请求**时反粘连照常生效（实测轮转到了另一个候选），
即"用户要换个答案"和"agent 续写"两种情况都符合预期。

## 未验证 / 已知限制

- 亲和键对"同一段对话的开头"敏感：用户手动改掉第一条 user 消息（或客户端改写
  system 注入内容）会被当成新会话，重新学习。这是刻意的，但会让 cache 复用
  在这些客户端上退化。
- TTL 30 分钟是拍的：更长的冷启动会话（隔夜继续）不会复用。没有实测校准。
- 亲和只影响**候选顺序**，不改打分、不做硬绑。因此即使亲和命中，若该候选已被
  熔断/限流，本轮仍然会正常换到下一个（这是 (1) 的要求，不是缺陷）。
- 表是内存态，进程重启即空；重启后第一轮重新学习，有一轮 cache 未命中。
