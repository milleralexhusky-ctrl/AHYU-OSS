# AHYU 4.30.14 请求分类：从"命中即判"到"证据累加"

versionCode 597

## 原判据的问题

    for (String w : CODE_WORDS) if (contains(w)) return CODE;

22 个词**等权**，命中任意一个立刻判 code。但这些词的证据强度差很多：

- 强信号（几乎只在编程语境出现）：```、堆栈、stacktrace、refactor、compile、debug、docker、sql、单元测试、正则、重构、编译
- 弱信号（日常中文也常用）：接口、异常、算法、报错、函数、脚本

"这个接口有点慢"、"今天有点异常"、"算法推荐不太准" —— 全都会被判成 code，
请求被推到 auto-code 池子，而那个池子的模型对普通对话未必更好。

## 改法：加权累加

    STRONG_CODE 每个 +2    WEAK_CODE 每个 +1
    累计 ≥ 2 判 code        （一个强信号，或两个独立弱信号）

离线对照（修完前后）：

| 文本 | 旧 | 新 |
|---|---|---|
| 这个接口有点慢 | code ✗ | chat ✓ |
| 今天有点异常 | code ✗ | chat ✓ |
| 算法推荐不太准 | code ✗ | chat ✓ |
| 帮我写一段代码 | code ✓ | code ✓ |
| ```python...``` | code ✓ | code ✓ |
| 这个函数报错了，stacktrace 在下面 | code ✓ | code ✓ |
| 帮我 refactor 这段 | code ✓ | code ✓ |

### 一处修正

第一版把"代码"放在 WEAK（1 分），结果"帮我写一段代码"只命中一个词、
得 1 分不够阈值，掉回 chat —— 而这句明明就是在要代码。
把"代码"提到 STRONG：这个词在日常对话里几乎不出现，出现基本就是编程。

## LONG_CHARS = 6000：验证失败，保留原值

本想用 usage.tsv 的 tokIn 列校准长文本阈值，但那一列**不可靠**：

    p50  = 69553 tok
    p99  = 261519 tok
    max  = 300614 tok

远超任何模型的上下文窗口。检查过写入路径（`c.tokIn = usage.input`）是对的，
所以问题在上游报回来的 usage 本身 —— 可能是累计值或含缓存。
**在不可靠的数据上调参，等于用一个错误换另一个错误。**

所以保留 6000，但在注释里写明：它没法用现有数据校准，
而且它只是"往长文池偏"而非硬门槛（判错代价不大，后面还有打分和兜底）。

## 真机验证（4.30.14）

    请求分类：code（代码证据 2（代码））           ← "帮我写一段代码"
