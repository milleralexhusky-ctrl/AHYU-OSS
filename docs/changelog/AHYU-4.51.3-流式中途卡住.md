# 4.51.3 — 流式中途卡住

## 起因

客户端反馈“思考过程中间卡住了”“输出过程中也在卡”：流已经开始，但上游突然不再
给新内容，客户端一直停在“思考中/输出中”。日志里出现 344 秒、97 秒的
`POST /v1/messages`，而网关没有任何超时提示。

查出三处：

1. `Http.stream` 的读超时是 **300 秒**：上游不关连接、也不发数据时，网关要等 5 分钟。
2. 已经出过内容后，内容看门狗仍按 **180 秒** 判定（这是按 p99.9 设的），
   交互场景下等于“卡三分钟”。
3. 超时通知的格式是 OpenAI 的 `data: {"error":…}`；Anthropic 客户端只认
   `event: error`，收到不认识的数据会继续等，于是看起来永远不结束。

## 改动

- **读空闲超时 300 秒 → 60 秒**（`Upstreams.STREAM_IDLE_MS`）：上游两次数据之间
  超过 60 秒就断开，抛出“上游流式响应超过 60 秒没有新数据，已断开”。
- **内容看门狗分两档**：
  - 还没出过内容：保留 180 秒兜底（首 token 预算通常更早触发）；
  - 已经出过正文/思考/工具调用：**80 秒**没有新内容就发超时错误。
  `Conn.sawContent` 由 text / thinking / toolCall / raw 回调置位。
- **超时错误按协议发送**：
  - Anthropic：`event: error` + `{"type":"error","error":{"type":"api_error",…}}`；
  - OpenAI / 其它：原来的 `data: {"error":…}` + `data: [DONE]`。
  `Conn.sseKind` 在 Anthropic 流开始写响应头时置为 `anthropic`。

## 验证

- 真机自检 36 / 36。
- Anthropic `auto` 流：首字节 3.4ms、总耗时 0.91s，事件序列正常。
- 超时路径为代码级验证：60 秒读超时由 `Http.stream` 的 `setReadTimeout` 保证；
  80 秒内容看门狗与协议错误格式由单元断言/代码路径确认。
- 没有真实“卡住”复现样本（上游行为），所以未宣称已在真实卡流上验证；
  下次出现时日志会出现“X 秒没有出字，已通知客户端（upstream_timeout）”。

## 说明

- 60 秒仍给推理模型留出了正常思考间隔；如果某个模型确实会在两段输出之间
  停顿超过 60 秒，它会被判超时并让客户端重试，这是为了交互响应性的取舍。
- 上游账号本身的速度/稳定性无法由网关改变；本轮解决的是“卡住时永远不结束”。
