# 4.57.0 — 11128「原样重发」的熔断：51 次重发、0 次放行

## 起因

4.50.4 给请求级风控（`11128 Illegal API invocation from an unapproved channel`，
官方提示「请重新发送」）加了一条策略：同账号原样重发 2 次，间隔 500ms / 1500ms。
依据是当时一次真实请求重放放行了。

翻真机日志时发现这条前提**已经不成立**：

```
20:16:00 [INFO] workbuddy 渠道校验：WorkBuddy 1 · 原样 风控拦截，第 1 次重发
20:16:02 [INFO] workbuddy 渠道校验：WorkBuddy 1 · 原样 风控拦截，第 2 次重发
20:16:04 [INFO] workbuddy 渠道校验：WorkBuddy 1 · 原样 请求级风控仍未放行
```

这类三段式序列在日志里出现 **51 次**（20:16 起、到次日 00:31），
而 `重发通过` 的计数是 **0**（两份日志都是 0）。

代价是实打实的，而且付在**请求线程**上：

- 每轮多 2 个上游往返；
- 多 2 次 `Thread.sleep`（500ms + 1500ms）= **2 秒**；
- 51 轮 × 3 次请求 = 153 次调用，全部落空。

更要紧的是上下文：这段时间两个账号**同时**在撞额度耗尽（14018），
一轮 `auto` 选路本来就要换 4~5 个候选。每个候选先白等 2 秒再失败，
一次客户端请求被拖到 **10 秒**（日志实测 `POST /v1/chat/completions 用时 10201ms`）。

## 改法：熔断，而不是删掉

不能直接删 —— 4.53.3 之前它确实救回过请求，"偶发拦截能重发过"是一条真实存在的路，
删了等于让那类请求失去唯一的补救。所以做成**按账号的熔断**：

| 状态 | 行为 |
| --- | --- |
| 正常 | 与现在完全一致：最多重发 2 次 |
| 连续 3 轮重发都没放行 | 该账号 10 分钟内**不再重发**，风控一到就直接换号/换模型 |
| 10 分钟后 | 自动恢复重发（重新验证上游是否又变得可重试） |
| 任一重发放行 | 立即清零，回到正常 |

关键细节：熔断打开时那一轮**不计数**（`resent[0] == 0`），
否则熔断会自己把自己永久锁死 —— 冷启动后第一次尝试永远失败，
计数继续涨，永远回不到正常。

## 验证

真机自检新增第 61 项「原样重发熔断（连续无效就停，成功即恢复）」，
断言四个方向：

- 初始允许重发；
- 前 2 次失败仍允许（阈值是 3，别把偶发拦截一并放弃）；
- 连续 3 次无效之后确实熔断；
- 一次成功之后立刻恢复。

自检 **61/61 通过**（真机，4.57.0）。

熔断触发时写一行应用日志：

```
workbuddy：WorkBuddy 1 原样重发连续 3 次都没放行，10 分钟内不再重发（省往返与 2 秒等待）
```

自检演练用假账号名（`自检-重发熔断-<纳秒>`）并对日志关闭、结束时从 map 移除，
不会污染真实账号状态，也不会在日志里留下假记录。

## 未做 / 边界（重要）

- **没有在真实 11128 场景下端到端验证熔断生效**。账号当前全部撞在额度/频率上
  （14018 / 6004），构造不出一次干净的"请求级风控"来观察它跳过重发。
  本版证据是**日志统计（51 次 / 0 次成功）+ 自检断言**，不是线上行为复现。
- 阈值（3 轮）和冷却（10 分钟）是拍定的，没有按真实分布调参 —— 因为样本里成功率恰好是 0，
  任何"成功率"都估不出来。如果后续日志里出现 `重发通过`，说明上游行为变了，
  这两个数应当重新评估。
- 只动 WorkBuddy 的这一个重发循环，不改 Router 的候选预算，也不动
  `channel`（账号级 11128）那条 6 小时回避。
